Автоматизация проводится по форме "Купить" (обычная оплата по дебетовой карте).
   
Валидные данные (общий набор для всех сценариев):
1.Номер карты (APPROVED): 1111 2222 3333 4444 (характеристика: валидный номер действующей карты, закрепленный в системе для успешных транзакций).
2.Номер карты (DECLINED): 5555 6666 7777 8888 (характеристика: валидный номер действующей карты, закрепленный в системе для отклонения транзакций).
3.Месяц: текущий календарный месяц в двухзначном формате (например, если сейчас июль — 07).
4.Год: текущий год плюс один год, в формате двух последних цифр (например, если сейчас 2026 год — 27). 
Данный подход гарантирует, что срок действия карты точно не истек, независимо от текущего месяца.
5.Владелец: случайно сгенерированное имя и фамилия на латинице в верхнем регистре. Пример: IVAN IVANOV.
6.CVC/CVV: три случайно сгенерированные цифры. Пример: 593

1. Позитивные сценарии (Happy Path)

ТК1: Успешная покупка тура по по APPROVED карте

Шаги: 
Выбрать форму «Купить».
Ввести номер карты: 1111 2222 3333 4444. 
Ввести валидные данные: месяц, год (будущий), имя владельца (латиница), CVC/CVV (3 цифры). 
Нажать «Продолжить».

Ожидаемый результат: 
Появляется всплывающее окно об успешной оплате. 
В СУБД PostgreSQL появляется запись со статусом APPROVED

ТК2: Покупка тура по APPROVED карте на граничном сроке действия (текущий месяц и год)

Выбрать форму «Купить»
Ввести номер карты: 1111 2222 3333 4444.
Ввести валидные данные: месяц, год (текущий), имя владельца (латиница), CVC/CVV (3 цифры).
Нажать «Продолжить».

Ожидаемый результат: 
Появляется всплывающее окно об успешной оплате, в БД — статус APPROVED.

ТК4:  Оплата картой с истекшим сроком действия (прошлый год)

Выбрать форму «Купить»

     Перечень используемых инструментов с обоснованием выбора

1. Язык программирования: Java — промышленный стандарт для автоматизации, имеющий строгую типизацию и развитую экосистему тестовых библиотек.
2. Сборщик проектов: Gradle — обеспечивает быструю сборку, гибкое управление зависимостями и простую конфигурацию тасок для запуска тестов.
3. Тестовый фреймворк: JUnit — современный стандарт, поддерживающий параметризованные тесты, удобные аннотации жизненного цикла (@BeforeEach, @AfterEach) и параллельный запуск.
4. Инструмент для UI-тестирования: Selenide — лаконичный синтаксис, автоматическое управление жизненным циклом браузера.
5. СУБД: PostgreSQL — легкие инструменты для выполнения прямого SQL-кода из тестов с целью верификации статусов транзакций в таблицах PostgreSQL.
6. Контейнеризация: Docker и Docker Compose — гарантируют идентичность окружения (СУБД PostgreSQL и симулятор банковских сервисов) на локальном компьютере.
7. Генерация тестовых данных: Java Faker — для динамического создания уникальных и реалистичных имен держателей карт на каждом запуске.
8. Отчетность: Allure report — строит детальные интерактивные отчеты с шагами, скриншотами упавших тестов и графиками стабильности.

         Перечень и описание возможных рисков при автоматизации

1.Проблемы с уникальностью локаторов на UI: возможно веб-элементы (поля ввода, кнопки) не имеют уникальных атрибутов id или data-test-id. Это увеличит риск падения тсетов.

        Интервальная оценка с учётом рисков (в часах)

1. Развертывание инфраструктуры (Docker Compose, запуск PostgreSQL, проверка подключения): 12 часов
2. Создание архитектуры проекта (Page Object, конфигурация Gradle, SQL-хелперы): 10-12 часов
3. Написание автотестов для формы «Обычная оплата»: 24–48 часов
4. Ручное тестирование формы «Купить в кредит» и оформление Issues по двум формам: 4–6 часов
5. Настройка Allure-отчетов: 3–5 часов
6. Подготовка финальной отчетности (итоги тестирования и автоматизации): 3–4 часа
   Итоговая интервальная оценка: 56 – 87 рабочих часов.
